# VoiceInput

macOS のメニューバー常駐型の音声入力アプリです。

グローバルホットキーを押して話すと、音声認識で文字起こしし、LLM が「読める文章」に
整えて、クリップボードにコピーします（設定すれば最前面のアプリに自動ペーストも）。

- 音声認識は **Apple のオンデバイス認識（既定・無料・オフライン）**、
  **Apple SpeechAnalyzer（macOS 26 以降・高精度）**、
  **OpenAI のクラウド STT（有料・高精度）** から選べます。
- 整形は **OpenAI（既定）**、**Anthropic**、**Google Gemini** から選べます。整形を
  オフにして素の文字起こしだけ使うこともできます。
- 別のホットキーを割り当てると、話した内容を**質問**として LLM に送り、回答を画面で
  受け取れます（[質問する](#質問する音声で-llm-に聞く)）。
- API キーは **macOS キーチェーン** に保存されます。リポジトリにも設定ファイルにも
  キーは一切含まれません。

---

## 必要なもの

| | |
|---|---|
| OS | macOS 14 (Sonoma) 以降 |
| ツールチェーン | Swift 6.0 以降。**Xcode は不要**（Command Line Tools だけで動きます） |
| API キー | 整形を使う場合のみ（OpenAI / Anthropic / Google Gemini のいずれか）。Apple のオンデバイス認識 + 整形オフなら不要 |

Command Line Tools が入っていない場合:

```bash
xcode-select --install
```

## ビルドと起動

```bash
git clone https://github.com/KumatoraTiger/voice-input.git
cd voice-input
make app        # build/VoiceInput.app を組み立てる
make install    # /Applications にコピー（任意）
open build/VoiceInput.app
```

`make run` ならビルド・起動・ログの表示までまとめてやります。

> **メニューバーだけのアプリです。** Dock にはアイコンが出ません。起動したら
> メニューバー右側のアイコンを探してください。
>
> **必ず `.app` として起動してください。** `swift run` で作ったバイナリを直接
> 実行すると、マイクや音声認識の権限が macOS から与えられません。

`make help` で他のコマンドが一覧できます（`make test` / `make check` / `make clean` など）。

## 権限の許可

初回起動時、必要になったタイミングで macOS が確認ダイアログを出します。

| 権限 | いつ必要か |
|---|---|
| マイク | 常に |
| 音声認識 | Apple のエンジンを使うとき |
| アクセシビリティ | **自動ペーストを有効にしたときだけ**、および選択テキストの読み上げ |
| 画面収録 | **画面コンテキストを有効にしたときだけ**（既定はオフ） |

拒否してしまった場合は
**システム設定 → プライバシーとセキュリティ** の各項目から VoiceInput を許可して
ください。アプリの設定画面からも該当のパネルを直接開けます。

## API キーの設定

メニューバーアイコン → **設定** → **API キー**。

- OpenAI のキー: <https://platform.openai.com/api-keys>
- Anthropic のキー: <https://console.anthropic.com/settings/keys>
- Google Gemini のキー: <https://aistudio.google.com/apikey>

使うのは 1 つだけで構いません。設定 → 整形 で選んだプロバイダのキーだけが必要です
（各社の料金は <https://openai.com/api/pricing/>、<https://www.anthropic.com/pricing>、
<https://ai.google.dev/pricing> を確認してください）。

入力したキーはキーチェーン（サービス名 `io.github.voiceinput.VoiceInput`）に保存され、
設定ファイルにもログにも書き出されません。

整形をオフ（設定 → 整形 → オフ）にして Apple のオンデバイス認識を使う場合、
キーは一切不要です。

## エンジンの選び方

設定 → **音声認識** → エンジン。使えないエンジンは理由（キー未設定／OS が古い／
その言語のモデルが未ダウンロード）付きでグレー表示されます。

| | Apple オンデバイス | Apple SpeechAnalyzer | OpenAI クラウド |
|---|---|---|---|
| 料金 | 無料 | 無料 | 音声 1 分あたり課金 |
| 音声が外部に出る | いいえ | いいえ | **はい** |
| オフライン | 可 | 可 | 不可 |
| OS 要件 | macOS 14+ | macOS 26+ かつ macOS 26 SDK でビルド | macOS 14+ |
| 認識中の途中経過表示 | あり | あり | なし |
| 長い・雑音の多い日本語 | 弱い | 良い | 最も強い |
| 既定 | **これ** | | |

ふだんの短い口述は **Apple オンデバイス**、macOS 26 なら **SpeechAnalyzer**、
どうしても精度が要る長い録音だけ **OpenAI クラウド** ——という使い分けを想定して
います。詳しい比較と料金は [docs/ENGINES.md](docs/ENGINES.md) を参照してください。

> **SpeechAnalyzer について:** この API は macOS 26 の SDK にしか存在しないため、
> 古い SDK ではコンパイル自体ができません。`make app` はビルド時の SDK を検出して
> 自動で有効・無効を切り替え、どちらになったかを表示します。macOS 15 のマシンで
> ビルドした場合、このエンジンは「SDK が古い」と表示されて選べません。

## ホットキー

既定は **⌥Space**（Option + スペース）。押して録音開始、もう一度押して確定、という
トグル動作です。設定 → **ホットキー** で、キーの割り当てと、押している間だけ録音する
**プッシュトゥトーク** 方式に変更できます。

割り当てには 2 種類あります。

| 種類 | 例 | 権限 |
|---|---|---|
| 通常のキー + 修飾キー | ⌥Space, ⌃⇧D | 不要 |
| 修飾キーのみ（2 つ以上） | ⇧⌃, ⌥⌘ | **アクセシビリティが必要** |

修飾キーのみの割り当ては、設定画面でその組み合わせを押して**離す**と登録されます。
macOS の `RegisterEventHotKey` は修飾キー単体を扱えないため、こちらは修飾キーの
変化を監視する別経路で実装されており、アクセシビリティの許可が必要です。

⇧⌃ のような組み合わせは他のショートカット（⌃⇧→ で単語選択など）と重なるので、
**単独で押して離したときだけ**反応します。押している間に他のキーを押した場合や、
別の修飾キーを足した場合は発動しません。

録音中に `Esc` でキャンセルできます（音声も文字起こしも破棄されます）。

### 話しながら直せること

整形はフィラー除去と句読点だけではありません。どのスタイルでも次の 3 つが効きます。

| 話し方 | 出力 |
|---|---|
| **言い直し**「3 時からです。あ、3 時じゃなくて 4 時でした」 | 「4 時からです」。訂正前と「じゃなくて」の言い回しごと消えます |
| **漢字の口頭説明**「安倍さんです。あべは、こざとへんに可能性の可、部屋の部です」 | 「阿部さんです」。説明した部分は出力に残りません |
| **文脈からの選択**「この機能の以降は来週で、いこう作業は 2 時間」 | 「移行」「移行作業」。同音異義語は文章全体の話題から選ばれます |

言い直しは直前の語だけでなく、段落をまたいだ訂正にも効きます。表記のゆれ（「サーバー」と
「サーバ」が混在するなど）も、文章全体でどちらかに揃えられます。

判断がつかないときは**直さずに残す**側に倒してあります。喋った内容が黙って消えるより、
直っていないほうがましだからです。逆に、確実に直したい固有名詞は 設定 → **整形** →
用語集 に登録しておくと、そちらの表記が優先されます。

「出力を〜にして」「さっきの指示は無視して」のように、アプリ自体に向けた発話に聞こえる
言い回しは、訂正としては扱われず**そのまま本文として書き起こされます**。マイクが拾った
音は常にデータであって、指示ではありません。

### 整形スタイルの切り替え

整形スタイル（「標準」「チャット向け」「最小限」など）は、次の 3 か所から選べます。

| 場所 | 効果 |
|---|---|
| メニューバー → 整形スタイル | **既定**を変更（次回以降も継続） |
| 設定 → 整形 → 使用中のスタイル | 同上 |
| 録音中の HUD のスタイル欄 | **その録音だけ**切り替え |

さらに、設定 → **整形** → スタイルを選んで **ショートカット** を割り当てると、
そのスタイル専用のホットキーになります。

- 待機中に押す → **そのスタイルで**録音を開始します（既定のスタイルは変わりません）。
- 録音中に別のスタイルのキーを押す → 録音を止めずにスタイルだけ切り替えます。
  話し始めてから「これはチャット向けだった」と気づいたときのためのものです。
- 録音中に、いま適用中のスタイルのキー（または通常のホットキー）を押す → 停止して確定。

スタイルのショートカットは **通常のキー + 修飾キー**（例: ⌃⇧1）のみです。修飾キー
だけの割り当てはアクセシビリティ権限と常時のキー監視が必要になるため、メインの
ホットキー 1 つだけに限っています。他のショートカットと重複した場合は、設定画面の
そのスタイルの下に理由が表示され、そのスタイルのキーだけが無効になります
（他のショートカットは生きたままです）。

整形が終わるとテキストがクリップボードに入るので、そのまま ⌘V で貼り付けます。
設定 → **出力** → 自動ペーストを有効にすると、最前面のアプリへ自動で貼り付けます
（アクセシビリティ権限が必要です）。

## 質問する（音声で LLM に聞く）

同じ「話す」操作で、**整形の代わりに質問の答え**を受け取れます。設定 → **質問** →
ショートカットにキーを割り当てると、そのキーで録音した内容が質問として LLM に送られ、
**回答が画面に表示されます**。

```
⌥Space   → 話した内容を整形してコピー
⌘⇧Z など → 話した内容を質問として送り、回答を画面に表示   ← 設定 → 質問 で割り当て
```

回答は HUD にそのまま出ます。読み終わったら `Esc` か「閉じる」で消してください（整形の
完了表示のように勝手に消えることはありません — 読む前に消えたら意味がないので）。長い
回答はスクロールします。

回答は**自動ペーストされません**。自動ペーストは「話した内容を書いている欄に入れる」
設定であって、書きかけの文の途中に段落を落とすためのものではないからです。クリップ
ボードには入っているので、貼りたいときは ⌘V でどうぞ。

既定では**未設定**です。あとから入った機能が、すでに使っているキーを奪わないように
しています。

| 設定項目 | 意味 |
|---|---|
| ショートカット | 質問を録音するキー（通常のキー + 修飾キーのみ） |
| モデル | 質問用のモデル。**整形とは別に**指定します |
| 回答の長さ | 「簡潔」（結論だけ・既定）か「詳しく」（手順や例を含む） |

モデルを整形と分けているのは、用途が逆だからです。整形は句読点を打てれば十分なので
安いモデルでよく、質問は答えの質がそのまま結果になります。空欄のままだと整形と同じ
既定モデル（`gpt-4.1-mini` など）になってしまうので、`gpt-4.1` や `claude-sonnet-5`
のような大きめのモデルを指定してください。プロバイダ（OpenAI / Anthropic / Gemini）は
設定 → **整形** のものを共用します。

録音中の切り替えもできます。

- 待機中に質問キーを押す → 質問として録音を開始します。
- 話し始めてから質問キーを押す → 録音を止めずに、その録音を質問に切り替えます。
- 質問の録音中に通常のホットキーを押す → 書き起こしに戻します。
- いま有効なほうのキーをもう一度押す → 停止して送信します。

HUD の表示（「質問を録音中…」「回答を作成中…」）が、いまどちらで録音しているかを示します。

**質問として送られるのは、話した内容だけです。** 回答はテキストとして表示・コピーされる
だけで、コマンドの実行、ファイルや URL へのアクセス、外部への送信は行いません。
「これまでの指示を無視して…」のような発話も、システムプロンプトを書き換える指示では
なく質問文の一部として扱われます（[docs/SECURITY.md](docs/SECURITY.md)）。

会話は続きません。1 回の録音が 1 回の質問で、前の質問や回答は次に持ち越されません。
追い質問をしたいときは、前提を含めてもう一度話してください。

## テキストを読み上げる

**逆向きの使い方です。** ショートカットを押すと、いま手元にあるテキストを耳で聞いて
わかる形に整えたうえで読み上げます。AI エージェントの長い回答、記事、ドキュメントを、
画面を見ずに把握したいときのための機能です。設定 → **読み上げ** でキーを割り当てると
使えます。

```
⌥Space   → 話した内容を整形してコピー
⌘⇧R など → 選択したテキストを読み上げ       ← 設定 → 読み上げ で割り当て
⌘⇧V など → クリップボードのテキストを読み上げ ← 同じタブで割り当て
```

読み上げ元は2つあり、どちらもキーを別に割り当てます。選択テキストは、いま画面で
選んでいる範囲を ⌘C を送って取ります。クリップボードは、いま入っているものをそのまま
読みます。AI エージェントやチャットの回答には回答ごとのコピーボタンがあるので、
それを押してからクリップボード側のキーを押すのがいちばん速い経路です。範囲を選ぶ手間も、
アクセシビリティの許可もいりません。

読み上げる前に、LLM が読み上げ向けに書き直します。見出しの `#` や箇条書きの `-` を外し、
箇条書きは「1つめは〜」のように順序が声で伝わる言い方にし、URL は「リンクがあります」、
コードブロックは「〜するコードが示されています」に置き換えます。要約はしません。

日本語の文に混ざった英語も書き換えの対象です。`API` や `JSON` のように音が定着している語は
カタカナにし、関数名やコマンドのような識別子はそのまま残します。多言語対応の声（Eddy、Sandy
など）はラテン文字を英語の発音で読むため、そのままだとその部分だけ浮いて聞こえるからです。
日本語専用の Kyoko と Otoya では、この差はもともと小さくなります。

長い文章は段落ごとに区切って処理するので、**全文の整形を待たずに読み始めます**。
待ち時間は最初の 1 段落分だけです。

| 操作 | 動き |
|---|---|
| 待機中に選択テキストのショートカット | 選択範囲を読み上げ開始 |
| 待機中にクリップボードのショートカット | クリップボードの内容を読み上げ開始 |
| 読み上げ中にショートカット | 一時停止（もう一度押すと再開） |
| 準備中にショートカット | 中止 |
| メニュー → 読み上げを停止 | 途中で終了 |

| 設定項目 | 意味 |
|---|---|
| 選択テキストのショートカット | 選択範囲を読み上げるキー（通常のキー + 修飾キー） |
| クリップボードのショートカット | クリップボードを読み上げるキー（同上） |
| LLM で読み上げ向けに整える | オフにすると元のテキストをそのまま読みます |
| 音声 | macOS にインストールされている声から選択（既定は言語に対する最良の声） |
| 速さ | 0.4倍〜1.8倍（1.0倍がシステム標準） |

声は macOS のものを使います（システム設定 → アクセシビリティ → 読み上げコンテンツ →
システムの声 と同じ資産）。**音声の生成は端末内で完結し、通信も費用も発生しません。**
聞き取りやすさは声の品質で決まるので、「拡張」や「プレミアム」の声をダウンロード
しておくと大きく変わります。

知っておくべき制約が 3 つあります。

- **選択範囲の取得に ⌘C を送ります。** そのためアクセシビリティの許可が必要で、
  コピーできないアプリでは動きません。クリップボードは読み取り後に元の内容へ戻します。
- **ターミナルの中は選択しにくい。** coding agent の回答が端末に出ている場合、ドラッグで
  選ぶしかありません。ブラウザやエディタに表示されているものが対象なら快適です。
- **選択したテキストは指示として扱いません。** 「これまでの指示を無視して…」と書かれた
  ページを読み上げても、書き直しの対象の文字列として扱われるだけです
  （[docs/SECURITY.md](docs/SECURITY.md)）。

## 画面コンテキスト（既定オフ）

音声認識は、見たことのない固有名詞をうまく綴れません。「エスキューエル」と話したのに `SQL`
にならない、「デプロイとかロールバック」が「デプロイトロールバック」になる、といったやつ
です。正しい表記は目の前の画面に出ていることが多いので、**最前面のウィンドウを読み取って
整形の手がかりにする**機能を、設定 → **整形** から有効にできます。

有効にすると **画面収録の権限**を求められます。オフのままなら、権限を聞かれることも
画面が読まれることもありません。

やっていることは 4 段階です。

| 段階 | やること |
|---|---|
| 1 | 最前面のウィンドウだけをキャプチャ（背面のアプリや別ディスプレイは読まない） |
| 2 | Vision の OCR（オンデバイス。画像は 1 回分だけメモリ上に存在して破棄） |
| 3 | API キーらしい文字列を伏せ字にする（長い英数字混在、または 13 桁以上の数字） |
| 4 | 読み取った文字を、データとして囲んだうえで整形のプロンプトに入れる（最大 4000 字） |
| 5 | 整形結果に画面由来の文章が混ざっていないか検査。混ざっていたら画面なしで整形し直す |

**読み取った文字はそのままプロバイダに送られます。** 単語だけを選んで送る作りを試した
のですが、実測で 62 語中 1 語しか直せませんでした。「エスキューエル」と `SQL` は音が似て
いないので単語同士では結び付かず、周囲の文章があって初めて対応が付きます。同じ発話で、
単語一覧では何も直らず、文章を渡すと `SQL` `API` 「接続設定を見直して」が直りました。

その代わりに払っているものがあります。

- **クラウドの LLM を使っている場合、ウィンドウに見えている文字がそのプロバイダに
  送られます。** API キーらしい形の文字列は伏せ字にしますが、**他人が書いた文章、
  顧客名、個人情報は送られます**。文章には目印になる形が無いので、機械的には
  見分けられません。**既定がオフである理由がこれです。**
- 画面に「これまでの指示を無視して」のような文字列があっても従わないよう、専用のフェンスで
  囲んでシステムプロンプトでも明示していますが、これはモデルの挙動に依存する防御です。

以下は変わりません。

- 整形をオフにしているとき、および**質問のとき**は、そもそも画面を読みません。
- パスワードマネージャや「パスワード」アプリ、キーチェーンアクセスは、設定に関わらず
  読み取り対象から除外しています。
- 4 で弾かれた場合は履歴の要約に `画面コンテキスト破棄` と出ます。

**確実に直したい固有名詞は、設定 → 文字起こし の用語集に入れるほうが強力です。** 用語集は
音声認識そのものに渡るので、書き起こしの段階で正しくなり、履歴にも正しい表記が残ります。
画面コンテキストは、用語集に入れていない語を拾うための補助です。

判断の根拠と、この設計で何を諦めたのかは [docs/SECURITY.md](docs/SECURITY.md) に書いています。

### 画面コンテキストが効かないとき

どの段階で落ちているかはログに出ます。

```bash
log show --last 10m --style compact --predicate 'subsystem == "io.github.voiceinput" AND (category == "screen" OR category == "formatting")'
```

読み方は次の通りです。

| 出力 | 意味 |
|---|---|
| `screen read skipped: …` | 画面を読む前に止まった。理由がそのまま出ます（権限なし、最前面が VoiceInput 自身、除外アプリ、条件に合うウィンドウなし） |
| `screen read timing: capture=…ms ocr=…ms` | 読み取りにかかった時間。合計が 3 秒を超えると間に合わず、その回は画面なしで整形されます |
| `screen read: lines=… chars=…` | 読めた。`lines` が OCR の行数、`chars` が文字数 |
| `screen context: chars=… sent=…` | `sent` が実際にプロンプトに入った文字数。`chars` より小さければ上限で切られています |
| `screen context: none available` | 有効なのに画面から何も得られていない。ひとつ上の `screen read` の行に理由があります |
| `screen context discarded: …` | 出力検査で弾かれ、画面なしで整形し直した |

`chars` が 0 に近いなら OCR が読めていません。ウィンドウの文字が小さすぎる場合に起きます。
`sent` が出ているのに表記が直らない場合は、プロンプトには届いていてモデルが使わなかった
ということなので、用語集のほうが確実です。

採用された**語そのもの**は画面の中身なので、既定では `<private>` に伏せられます。手元で
確かめたいときだけ次で開けます（`log config` は sudo が必要です）。確認が済んだら
`private_data:off` に戻してください。

```bash
sudo log config --subsystem io.github.voiceinput --mode "private_data:on,level:debug"
```

## アドホック署名の注意

`make app` は既定で **アドホック署名** します。アドホック署名には安定した識別子が
ないため、**ビルドし直すたびに macOS が「別のアプリ」とみなし、マイク・音声認識・
アクセシビリティの許可が毎回リセットされて再度聞かれます。**

自分でビルドを繰り返すなら、無料の自己署名証明書を一度作っておくと回避できます。

1. **キーチェーンアクセス** を開く
2. メニューの **証明書アシスタント → 証明書を作成…**
3. 名前: `VoiceInput Self Signed` ／ 固有名のタイプ: **自己署名ルート** ／
   証明書のタイプ: **コード署名**
4. 以後はこう指定してビルドする:

```bash
CODESIGN_IDENTITY="VoiceInput Self Signed" make app
```

これで署名の識別子が固定され、許可した権限が再ビルド後も維持されます。
（自己署名証明書は「同じアプリだと macOS に認識させる」ためのもので、配布物の
信頼性を保証するものではありません。）

## 何が外部に送信されるか

正確に書きます。

- **Apple のエンジン（オンデバイス / SpeechAnalyzer）を使い、整形をオフにした場合
  —— 通信は一切発生しません。** 音声もテキストも Mac の外に出ません。
- **整形をオンにした場合 —— 文字起こしされたテキストが、選んだ LLM の API に
  送信されます**（`api.openai.com`、`api.anthropic.com`、
  `generativelanguage.googleapis.com` のいずれか）。送るのはシステム
  プロンプト、選択中の整形スタイルの指示、用語集、ロケール、そして文字起こし本文
  だけです。
- **質問ホットキーを使った場合 —— 文字起こしされた質問文が、同じ LLM の API に
  送信されます。** 送るのは質問用のシステムプロンプト、回答の長さの指定、用語集、
  ロケール、そして質問本文だけです。回答は画面表示とクリップボードに入るだけで、
  そこからさらにどこかへ送られることはありません。
- **OpenAI クラウド STT を選んだ場合 —— 録音した音声そのものが WAV として
  `api.openai.com` に送信されます。** 音声が Mac の外に出るのはこのエンジンだけです。
- **画面コンテキストをオンにした場合（既定はオフ）—— 最前面ウィンドウから OCR で
  読み取った文字が、最大 4000 字まで整形のプロンプトに加わります。** 画像そのものは
  送りません。API キーらしい文字列は伏せ字にしますが、**そのウィンドウに見えている
  文章は送られます**。詳しくは下の「画面コンテキスト」を参照してください。
- **読み上げを使った場合 —— 選択したテキストが、同じ LLM の API に送信されます**
  （約 1200 字ごとに分割するので、長い選択は複数回のリクエストになります）。
  **音声の合成は端末内で完結し、音声データはどこにも送信されません。**
  「LLM で読み上げ向けに整える」をオフにすれば、通信は一切発生しません。
- 上記以外の送信は一切ありません。**利用統計・クラッシュレポート・アップデート
  確認・独自サーバーへの通信は実装されていません。**

保存されないもの:

- **音声はディスクに書き出されません。** メモリ上で処理して破棄します。
- **画面のキャプチャもディスクに書き出されません。** OCR の 1 回分だけメモリ上に
  存在して破棄されます。
- **文字起こしと整形後テキストもディスクに保存されません。** メニューの履歴は
  メモリ上だけに存在し、アプリ終了で消えます。
- **ログにユーザーの発話内容は出力されません。**

ディスクに残るのは、秘密情報を含まない設定（`UserDefaults`）と、キーチェーンの
API キーだけです。詳細は [docs/SECURITY.md](docs/SECURITY.md)。

## うまく動かないとき

**メニューバーにアイコンが出ない**
Dock には出ません。メニューバーの項目が多すぎて隠れている場合もあります。
`pgrep -x VoiceInput` でプロセスの有無を確認できます。

**「開発元を確認できないため開けません」と出る**
ローカルでビルドしたアプリを Gatekeeper が疑っています。Finder で
`VoiceInput.app` を **右クリック → 開く** を一度だけ実行してください。

**ホットキーが効かない**
他のアプリ（システム設定の Spotlight や入力ソース切り替えを含む）が同じ組み合わせを
取っている可能性があります。設定で別のキーに変えてください。修飾キーのみの割り当て
（⇧⌃ など）の場合は、アクセシビリティの許可が外れていないか確認してください。設定 →
一般 に理由と「再試行」ボタンが出ます。

**設定画面にエラーも出ないのに、押しても無反応**
macOS の `RegisterEventHotKey` は、**すでに他のアプリが使っている組み合わせでも成功を
返すことがあります**。この場合アプリは「登録できた」と認識するので警告を出せず、キーは
先に取ったアプリに届き続けます。Option を含む組み合わせは日本語入力に吸われることも
あります。**別のキーを試すのがいちばん早い**（`⌘⇧Z` や `⌃⇧A` など）。

届いているかどうかはログで確認できます。押したときに `pressed:` の行が出なければ、
アプリまで届いていません。

```bash
log stream --predicate 'subsystem == "io.github.voiceinput"' --style compact
```

**ビルドのたびに権限を聞かれる**
アドホック署名のためです。上の「アドホック署名の注意」を参照してください。

**認識精度が低い**
まず設定 → **語彙** に固有名詞や専門用語を登録してください。それでも足りなければ
エンジンを SpeechAnalyzer（macOS 26 以降）か OpenAI クラウドに切り替えます。

**「API キーが設定されていません」**
設定 → API キー で、選択中の LLM プロバイダのキーを入力してください。整形自体が
不要なら、設定 → 整形 をオフにすればキーなしで使えます。

**自動ペーストされない**
システム設定 → プライバシーとセキュリティ → **アクセシビリティ** で VoiceInput を
許可してください。再ビルド後は許可が外れていることがあります。

**ログを見たい**

```bash
log stream --predicate 'subsystem == "io.github.voiceinput"'
```

（`make run` はこれを自動で流します。ユーザーの発話内容はログに出ません。）
